# STEEL MIND — 제철소 AI Agent 의사결정 시뮬레이션 기획안

> **기획 기록:** 팀 철든신입 · POSCO K-뉴딜 아카데미 내부 해커톤(2026-11-09~11-10). 이 문서는 초기 설계 문서 3개(게임 시스템 설계서, Agent 구조 설계서, 통합 기획안)를 하나로 합친 것이다. 문서에 나오는 공장 상태값·가중치·임계값은 모두 **게임 밸런스용 가상 수치**이며 실제 제철소 기준이 아니다. 실제 설비 제어나 실시간 산업 데이터와는 관계가 없다.

## 1. 문제 정의 및 기획 의도

제철소의 의사결정에는 생산·품질·설비·안전·에너지·환경·물류 부서의 목표가 함께 걸려 있다. 한 부서에 맞는 판단이 다른 부서에는 손해가 되는 경우가 많다. 예를 들어 납기를 맞추려고 속도를 유지하면 설비와 안전 위험이 커진다.

지금의 AI 체험은 대부분 프롬프트를 쓰거나 코드를 생성하는 데 그친다. 업무 맥락에서 **여러 AI Agent가 서로 다른 목표로 제안하고 충돌할 때 사람이 무엇을 판단해야 하는지**를 체험할 기회는 드물다.

STEEL MIND는 플레이어가 가상 제철소의 운영 책임자가 되어 Agent들의 상충하는 제안을 비교하고 최종 결정을 내리는 시뮬레이션 게임이다.

| 구분 | 내용 |
| --- | --- |
| 대상 사용자 | 제철소 공정과 부서 간 이해관계를 처음 접하는 신입사원·교육생 |
| 플레이어 역할 | 가상 제철소 운영 책임자 |
| AI의 역할 | 부서별 목표를 가진 Agent로서 근거와 함께 대응안을 제안한다. 결정하지 않는다 |
| 사람의 역할 | 제안의 트레이드오프를 비교해 최종 대응안을 고른다 |
| 결과 계산 | 규칙 엔진이 사전 정의된 상태 변화값을 적용한다. 같은 선택은 항상 같은 결과를 낸다 |

**설계 원칙**

- **AI는 제안하고 사람은 판단한다.** Agent 출력은 화면 표시와 충돌 분석에만 쓰고, 점수나 공장 상태를 직접 바꾸지 않는다.
- **결과는 재현 가능해야 한다.** 점수와 상태 변화는 규칙 엔진이 계산하므로 시연을 반복해도 결과가 같다.
- **한 사건을 끝까지 완성한다.** 사건 수를 늘리기보다 사건 1개를 알림부터 결과·후속 사건까지 완성하는 것을 우선한다.

## 2. 게임 설계

### 플레이 루프

```
공장 상태·사건 확인 → Agent 의견·근거 확인 → 충돌·예상 영향 비교
→ 대응안 선택 → 상태·점수 갱신 → 결과 리포트 → 후속 사건
```

### 상태 지표

모든 지표는 0~100 범위의 가상 값이다. 갱신 후에도 0~100 범위를 벗어나지 않게 제한한다.

| 지표 | MVP 노출 | 비고 |
| --- | :---: | --- |
| 생산성 | ○ | 생산량·납기 |
| 품질 | ○ | 규격·불량 |
| 안전 | ○ | 작업자 위험 |
| 설비 안정성 | ○ | 고장 위험·가동률 |
| 에너지 효율 | | 확장 |
| 환경 준수 | | 확장 |
| 비용 효율 | | 확장 |

### MVP 사건: 압연 과열 + 전력 제한

압연 설비 온도가 오르는 중에 전력 사용 제한이 걸린다.

| Agent | 주장 |
| --- | --- |
| 생산 | 납기를 위해 속도 유지 |
| 설비 | 감속 후 점검 |
| 품질 | 온도가 품질에 주는 영향 확인 |
| 안전 | 위험 구역 통제 |
| 에너지 | 부하 분산 |
| 물류 | 생산 순서 유지 |

| 선택지 | action ID | 생산성 | 품질 | 안전 | 설비 안정성 |
| --- | --- | :---: | :---: | :---: | :---: |
| A. 속도 유지 | `keep_speed` | ▲ | ▼ | ▼ | ▼ |
| B. 감속 및 점검 | `slow_and_inspect` | ▼ | ▲ | ▲ | ▲ |
| C. 일시 정지 및 통제 | `pause_and_control` | ▼▼ | – | ▲▲ | ▲ |

화살표는 방향만 나타낸다. 실제 delta 값은 시나리오 데이터에서 원민이 정한다.

### 점수·승패 규칙

- 선택지마다 사전 정의된 상태 변화값(delta)을 적용한다.
- 총점은 지표별 가중 합으로 계산한다. 초안의 테스트용 가중치는 생산성 30%, 품질 25%, 안전 35%, 비용 효율 10%이다.
- **안전 게이트:** 안전 지표가 하한선 아래로 떨어지면 총점과 관계없이 성공 판정을 내리지 않는다.
- **확정 필요:** 초안의 가중치에는 비용 효율이 들어 있지만 MVP에서 노출하는 지표는 설비 안정성이다. 가중치를 노출 지표 4개(생산성·품질·안전·설비 안정성) 기준으로 맞출지 첫날 오전에 정한다.

### 난이도

| 난이도 | 활성 Agent | 사건 구성 |
| --- | --- | --- |
| Easy | 2~3개 | 단일 사건 |
| Normal | 4~5개 | 연속 사건, 자원 제약 |
| Hard | 6~7개 | 시간·예산 제약, 복합 사건 |

MVP는 Normal 수준의 사건 1개와 후속 분기로 구성한다.

## 3. Agent 구조 및 시스템 설계

### Agent 구성

| Agent | 목표 | 주로 충돌하는 Agent |
| --- | --- | --- |
| 생산 | 생산량·납기 달성 | 품질, 설비, 안전, 에너지 |
| 품질 | 규격·불량 관리 | 생산, 비용 |
| 설비 | 고장 예방·가동률 | 생산, 비용 |
| 안전 | 작업자 위험 최소화 | 생산 |
| 에너지 | 에너지 사용 최적화 | 생산, 물류 |
| 환경 | 배출·환경 목표 | 생산, 에너지 |
| 물류 | 원료·제품 흐름, 출하 | 생산, 비용 |

사건마다 관련 Agent만 활성화한다. 모든 Agent를 매 사건에 출연시키지 않는다.

### 충돌 유형

| 유형 | 예시 |
| --- | --- |
| 목표 충돌 | 생산 증대 vs 안전 위험 감소 |
| 자원 충돌 | 정비 예산 vs 비용 절감 |
| 시간 충돌 | 검사 시간 vs 납기 |
| 정보 충돌 | 같은 현상에 대한 다른 관측·해석 |
| 연쇄 충돌 | 이번 선택의 결과가 다음 사건에서 다른 Agent의 요구를 만든다 |

충돌 관계는 사건 데이터에 명시해 구현과 테스트가 가능하게 한다.

### Agent 입출력

- **입력:** 사건·공정 설명, 현재 상태값, Agent 목표, 제약 조건, 허용된 대응 범위
- **출력 예시:**

```json
{
  "agent_id": "equipment",
  "position": "감속 후 점검을 권고",
  "reasoning_summary": "온도 상승 추세가 설비 위험을 높임",
  "recommended_action": "slow_and_inspect",
  "expected_impacts": {
    "productivity": "decrease",
    "equipment_stability": "increase"
  },
  "confidence": 0.78,
  "conflicts_with": ["production", "logistics"]
}
```

### 실행 흐름과 모듈

```
Scenario Manager(사건·상태 로드) → Agent Selector(참여 Agent 선택)
→ Agent Layer(제안 생성) → Conflict Layer(충돌 정리) → UI(제안·충돌 표시)
→ 플레이어 선택 → Rules Engine(delta 적용) → Scenario Manager(후속 사건 결정)
```

| 모듈 | 주고받는 것 |
| --- | --- |
| Scenario Manager | 사건 ID, 현재 상태, 후속 사건 |
| Agent Layer | Agent별 제안(위 JSON 형식) |
| Conflict Layer | 충돌 상대와 상충 지점 요약 |
| Rules Engine | action ID를 받아 delta 적용, 갱신된 상태·점수 반환 |
| UI | 사건·Agent 제안·선택지·결과 표시 |

### LLM 사용 범위와 신뢰 경계

- **MVP:** Agent 제안은 사전 정의된 시나리오 데이터로 제공한다. API 없이도 역할·충돌·분기 경험이 완성되고, 시연 재현성이 높다.
- **확장:** LLM은 Agent 발언 문장, 상황 설명, 결과 요약 생성에만 쓴다. 행동 선택과 점수 계산은 규칙 엔진이 맡는다.
- LLM 출력은 스키마로 검증한다. 허용된 action ID 밖의 행동을 제안하면 거부하고 정적 시나리오 문장으로 대체한다.
- LLM 텍스트를 상태 변경 명령으로 직접 쓰지 않는다. 모든 선택은 사전 정의된 action ID에 매핑한다.
- 가상 시나리오와 가상 상태값만 사용하고, 실제 설비 명령은 실행하지 않는다.

## 4. 역할 분담 및 협업 방식

| 이름 | 담당 | 주요 산출물 |
| --- | --- | --- |
| 박소영 | 게임 시스템 설계, Agent 구조 설계, 전체 통합·기획안 | 기획안, 모듈 인터페이스(JSON 형식), 통합 빌드, 발표 스토리·데모 구성 |
| 양수빈 | 기존 게임 UI를 제철소 테마로 변경, 제철소 배경 | 공장 대시보드·사건 알림·선택 화면, 제철소 배경 이미지 |
| 신원민 | 미션 시나리오, 점수 계산 로직·기획안 | 사건·선택지·후속 분기 데이터, delta 표, 가중치·안전 게이트 규칙 |
| 김다영 | AI Agent 응답, 결과 화면 | Agent 제안 데이터(필요 시 LLM 문장 생성), 결과 리포트 화면 |

**모듈 경계**

| 연결 지점 | 보내는 쪽 → 받는 쪽 | 합의 내용 |
| --- | --- | --- |
| 시나리오 → 규칙 엔진 | 원민 → 원민·소영 | 사건 ID, 선택지 action ID, delta 표 |
| 시나리오 → Agent 응답 | 원민 → 다영 | 사건별 활성 Agent, 충돌 관계 |
| Agent 응답 → 화면 | 다영 → 수빈 | Agent 출력 JSON 형식 |
| 규칙 엔진 → 결과 화면 | 원민 → 다영 | 갱신된 상태값, 변화량, 총점, 안전 게이트 결과 |
| 전체 화면 흐름 | 소영 → 전원 | 대시보드 → 알림 → 브리핑 → 충돌 비교 → 선택 → 결과 → 다음 사건 |

**협업 방식**

- 첫날 오전에 모듈 경계의 JSON 형식을 `schemas/`에 확정한다. 이후 바꿀 때는 받는 쪽 담당자와 먼저 합의한다.
- 각자 먼저 가짜 데이터로 자기 모듈을 만들고, 형식이 확정되면 실제 데이터로 바꾼다. 다른 사람의 작업을 기다리지 않게 하기 위해서다.
- 정해진 시간마다 짧게 진척을 공유하고(아래 일정의 점검 시점), 막힌 부분은 그 자리에서 담당을 다시 나눈다.
- `main`에 직접 올리지 않는다. 브랜치에서 작업하고 Pull Request로 합치며, 다른 팀원 1명 이상이 승인해야 합친다.
- Pull Request 설명에 "무엇을, 왜 바꿨는지와 부딪힌 문제를 어떻게 풀었는지"를 남긴다. 이 기록이 개인별 기여와 문제 해결 과정의 근거가 된다.

## 6. 예상 결과물

- **플레이 가능한 게임 빌드:** 압연 과열 + 전력 제한 사건 1개를 알림부터 결과·후속 사건까지 진행할 수 있다.
- **화면:** 공장 대시보드, 사건 알림, Agent 브리핑(Agent별 목표와 의견 구분), 충돌 비교, 대응안 선택(3개), 결과 리포트(최종 지표와 변화량, 선택의 이득·손실, Agent별 목표 달성도, 후속 사건, 운영 평가).
- **시나리오·규칙 데이터:** 사건, 활성 Agent, 충돌 관계, 선택지별 delta, 가중치, 안전 게이트.
- **발표 자료와 시연:** 아래 데모 흐름을 따른다.
  1. 압연 과열·전력 제한 알림
  2. 생산은 납기 방어, 설비는 감속, 안전은 통제를 주장
  3. 품질·에너지·물류 Agent가 추가 영향 제시
  4. 플레이어가 속도 유지 / 감속 점검 / 일시 정지 중 선택
  5. 상태값 갱신과 결과 표시
  6. 결과에 따라 후속 사건 발생

**완료 기준**

| 기준 | 확인 방법 |
| --- | --- |
| 처음 보는 사람이 짧은 안내만으로 미션을 끝낸다 | 팀 밖 1명에게 시연해 본다 |
| 플레이어가 Agent 간 충돌을 알아본다 | 브리핑 화면에서 충돌 상대와 상충 지점이 보인다 |
| 선택에 따라 결과가 눈에 띄게 다르다 | 선택지 A·B·C의 결과 화면을 나란히 비교한다 |
| 같은 입력은 같은 결과를 낸다 | 같은 선택을 반복해 상태값이 같은지 확인한다 |
| 팀원 모두 모듈 책임과 데이터 흐름을 설명할 수 있다 | 리허설에서 각자 자기 모듈을 설명한다 |

**범위에서 뺀 것:** 실제 설비 제어, 실시간 산업 데이터, 멀티플레이, 정밀 물리 시뮬레이션.

## 7. 현업 적용 가능성

- **신입 교육:** 부서 간 목표가 어떻게 부딪히는지를 사례 중심으로 체험하게 한다. 사건과 선택지는 데이터로 분리되어 있어 교육 담당자가 공정별 사건을 추가할 수 있다.
- **AI 협업 감각 훈련:** AI가 그럴듯한 근거로 제안해도 최종 판단과 책임은 사람에게 있다는 점을 체험하게 한다.
- **확장 방향:** 다른 공정(제선·제강 등)의 사건 추가, 난이도별 Agent 수 조정, 결과 기록을 활용한 교육 피드백.
- **한계:** 상태값과 가중치는 가상 수치이므로 실제 공정 판단의 근거로 쓰지 않는다. 현업에 쓰려면 현업 담당자의 시나리오 검토가 필요하다.
