# 판정 엔진 (재작성 v1.1)

설비 알람의 측정값을 보고 센서 문제인지 설비 문제인지 가린다. 못 가리면 확정하지 않고, 무엇을 한 번 재면 갈리는지 알려 준다. 결과는 판정 카드(JSON)로 낸다.

기획서 v0.4~v0.7, results.html, SCQA 기획안에 적힌 판정 논리를 새로 구현했다. **이전 v0.7 코드는 남아 있지 않아서, 기획서의 숫자(블라인드 1~8, 위험 오분류 1.8% 등)는 이 코드로 재현되지 않는다.** 숫자는 새 블라인드 데이터로 다시 잰다.

## 빠른 시작

Python 3.10 이상, numpy만 있으면 된다. 명령은 레포 루트에서 실행한다.

```bash
pip install -r engine/requirements.txt

# 판정 한 번 (기획서 6번 사례: 베어링 열화 + 온도센서 고착)
python -m engine judge --run engine/tests/example-06.csv

# 현장 확인 결과를 넣어 다시 판정 (휴대용 진동계 3.95 mm/s)
python -m engine judge --run engine/tests/example-06.csv --check vib=3.95

# 판정 카드 API (화면·LLM 연동용)
python -m engine serve --port 8000

# 테스트
python -m pytest engine/tests -q
```

기본 모델 `engine/models/dev-model.json`은 내부 모의 정상 회차 12개로 배운 개발용이다. 실측 데이터를 쓰면 그 정상 구간으로 다시 배운다.

```bash
python -m engine train --normal <정상 운전 CSV 폴더> --out engine/models/<이름>.json
```

## 입력 형식

1초 간격 CSV. 열 이름은 아래와 같아야 한다.

| 열 | 뜻 | 단위 |
|---|---|---|
| `t` | 운전 시작부터 지난 시간 | 초 |
| `setpoint` | 속도 설정값 | % |
| `torque` | 인버터 토크 추정값 | % 정격 |
| `current` | 모터 전류 | A |
| `vib` | 진동 (RMS) | mm/s |
| `temp` | 모터 온도 | °C |

- 처음 30~150초는 설비별 재보정 구간이다. 고장이 이 구간 안에 있으면 재보정이 고장을 흡수한다.
- 징후는 150초 이후부터 찾는다.

## 판정 흐름 (기획서 대응)

| 단계 | 하는 일 | 코드 |
|---|---|---|
| ① 가상센서 | 정상 운전에서 설정값→토크, 토크→전류, 설정값→진동, 토크 이력→온도(빠른·느린 두 열 경로)를 배운다 | `model.py` |
| 재보정 | 30~150초 잔차 중앙값을 0으로 맞춘다 | `detect.py` |
| 징후 | 잔차가 4σ를 넘어 이어지면 징후로 본다. 설정값 변경 직후 40초는 문턱 1.75배. 진동 간헐 튐과 온도 고착은 따로 찾는다 | `detect.py` |
| ② 후보 | 고장 징후표(설비 3, 센서 5)로 징후를 설명하는 후보를 남긴다 | `signatures.py`, `judge.py` |
| 판정 | 후보가 모두 설비 쪽이면 측정 확인됨 + 설비 후보 있음, 모두 센서 쪽이면 측정 의심 + 설비 징후 없음, 모두 설비+센서면 측정 일부 의심 + 설비 후보 있음. 섞이면 늦은 징후로 가를 수 있을 때 확인 대기(온도 지연의 2배까지), 아니면 정보 부족 + 현장 확인 항목 | `judge.py` |
| ④ 갱신 | 휴대용 계측 결과를 넣으면 후보를 줄여 다시 판정한다 | `judge.py` |

## 판정 카드

예시: `schemas/verdict-card.example.json`(현장 확인 전), `schemas/verdict-card.after-check.example.json`(진동계 확인 후).

카드는 **측정 상태**와 **설비 진단 상태**를 따로 적는다 (기획서 4.3). 센서를 배제했다고 설비 고장이 확정되지는 않는다. 정상 운전 변화, 모델 오류, 알려지지 않은 원인이 남기 때문이다. 화면과 정비 가이드는 이 두 상태를 쓴다.

| 경우 | `measurement_status` | `equipment_status` | `next_steps` |
|---|---|---|---|
| 징후 없음 | 확인됨 | 징후 없음 | (없음) |
| 설비 쪽 징후, 센서 후보 없음 | 확인됨 | 후보 있음 (`equipment_basis`: 설비 쪽 징후) | 정비 가이드로 넘김 |
| 현장 확인으로 센서 정상 | 확인됨 | 후보 있음 (`equipment_basis`: 센서 배제로 남은 후보) | 정비 가이드로 넘김 |
| 후보가 모두 센서 쪽 | 의심 | 징후 없음 | 계측 점검 |
| 설비 이상 + 센서 이상 | 일부 의심 | 후보 있음 | 정비 가이드로 넘김, 계측 점검 |
| 늦은 징후를 기다리면 갈림 | 확인 대기 | 판단 보류 | 재판정 대기, 현장 확인 |
| 지금 센서로 못 가름 | 정보 부족 | 판단 보류 | 현장 확인 (가를 계측기가 없으면 현업 판단) |

| 필드 | 뜻 |
|---|---|
| `measurement_status` | 센서 값을 믿어도 되는가: `확인됨` / `의심` / `일부 의심` / `확인 대기` / `정보 부족` |
| `equipment_status` | 설비 쪽 이상이 있는가: `후보 있음` / `징후 없음` / `판단 보류`. 설비 원인은 "확정"이라 쓰지 않는다 |
| `equipment_basis` | 설비 후보의 근거: `설비 쪽 징후` / `센서 배제로 남은 후보` |
| `next_steps` | 다음 할 일 (앞쪽이 먼저) |
| `handoff_to_guide` | 정비 가이드(LLM)로 넘겨도 되는가. 측정이 확인됨·일부 의심이고 설비 후보가 있을 때만 `true` |
| `handoff_note` | 넘길 때 같이 적을 말 (예: "설비 원인은 후보다", "의심 센서 값은 빼고 넘긴다") |
| `suspect_sensors` | 믿으면 안 되는 센서. 정비 가이드에 이 값은 빼고 넘긴다 |
| `findings` | 고장마다 `확정` 또는 `후보`. **`확정`은 센서 이상에만 쓴다** (현장 계측이나 고착처럼 물리적으로 불가능한 신호로 확인됨). 설비 원인은 언제나 `후보` |
| `candidates` | 징후를 설명하는 고장 조합 목록 |
| `check` | 다음 현장 확인: 계측기, 위치, 시간, 기록 방식, 읽는 법(`read_rule`), 결과별로 남는 후보 |
| `check.example_values`, `check.example_note` | 예시값인 항목. 시간·기록 방식·허용오차는 현업 절차를 확인하기 전까지 예시값이다. 화면과 안내문에 "예시값"으로 보여 준다 |
| `wait_until_s` | 확인 대기일 때 다시 볼 시각 |
| `checks_applied` | 넣은 현장 확인 결과와 판단 (휴대용 값, 설치 값, 가상센서 값, 허용오차, `tolerance_is_example`) |
| `values` | 관련 채널의 설치 센서 값과 가상센서 값 |
| `symptoms`, `reasons` | 보인 징후와 판단 이유 (화면에 그대로 쓸 수 있는 문장) |
| `verdict`, `verdict_detail` | **채점용 범주.** `정상` / `확정`(+ `센서`·`설비`·`동시`) / `확인 대기` / `정보 부족`. 화면에 "설비 확정"으로 보여 주지 않는다 |

API는 `POST /judge`에 `{"run": {열: [값...]}, "coupled": false, "checks": [...]}`를 보내면 판정 카드를 돌려준다.

**정비 가이드(LLM)에는 근거 카드를 넘긴다** (`handoff.py`, 예시 `schemas/evidence-card.example.json`). 판정 카드에서 가이드가 읽을 것만 남기고, 의심 센서의 값은 빼고 뺐다는 사실만 적는다. `POST /judge?view=evidence` 또는 `python -m engine judge --run <csv> --evidence`.

v1.0에서 바뀐 것: `evidence_status`를 없애고 `measurement_status`·`equipment_status`·`equipment_basis`·`next_steps`·`handoff_note`를 넣었다. 설비 쪽 `findings`는 `확정` 대신 `후보`로 나온다. 보류 중인 카드에도 확정된 센서 이상은 `suspect_sensors`에 넣는다. 결합 모드와 E25로 클램프미터를 기다릴 때는 전류센서도 `후보`로 적는다.

## 비교 기준: 현장 첫 판단 규칙 (H1)

이전 비교군(v0.2) 코드도 남아 있지 않아서 비교 기준을 새로 만들었다 (`baseline.py`).

- 아무 채널도 안 벗어나면 정상
- 센서 채널(전류·진동·온도) 하나만 벗어나고 토크(부하)는 그대로면 그 센서 고장
- 토크가 함께 벗어나거나 두 채널 이상이 벗어나면 설비 고장

징후 찾기는 판정 엔진과 똑같다. 그래서 차이는 판정 논리에서만 나온다. 이 규칙은 보류하지 않는다.

```bash
python -m engine batch --runs <폴더>/runs --out base.jsonl --rule baseline
```

## 재작성하면서 정한 것 (기획서에 없던 것)

1. **단일 고장 우선.** 단일 고장으로 설명되면 단일 후보만 남기고, 아니면 이중 후보를 남긴다.
   - 기획서는 "단일·이중 후보를 모두 남김"이었지만, 그러면 늦은 징후가 나타나도 후보가 갈리지 않았다.
2. **진동 기대값은 설정값만으로 계산한다.** 정상 데이터에서는 토크가 설정값에 묶여 있어 둘의 효과를 가를 수 없다. 토크를 넣었더니 부하가 바뀔 때 가짜 "진동 낮음" 징후가 나왔다.
3. **설비별 이득 차이만큼 문턱을 넓힌다.** 재보정은 오프셋만 맞춘다. 운전점이 재보정 구간에서 멀어지면 설비마다 다른 이득이 가짜 징후를 만든다. 정상 회차에서 잔차 기울기를 재서, 그 RMS의 `alpha_k`배만큼 문턱을 넓힌다.

   | 여유 배수 | dev101 기대비용 | dev202 기대비용 | 위험 오분류 |
   |---|---|---|---|
   | 1배 | 0.77 | 1.24 | dev202 1.6% |
   | **2배 (채택)** | **0.75** | **0.78** | **0%** |
   | 3배 | 1.90 | 1.98 | 2.4%, 3.2% (둔해져서 설비 징후를 놓침) |

4. **현장 확인 판단 방식.**
   - 휴대용 값과 설치 값의 차이가 계측기 허용오차 안이면 센서 정상으로 본다.
   - 허용오차를 넘으면 설치 값과 가상센서 값 중 휴대용 값에 가까운 쪽으로 판단한다 (E30).
   - 고정 허용오차(1 °C)만 썼을 때는 작은 온도 드리프트를 "센서 정상"으로 잘못 봤다.
5. **결합 모드(토크 추정값이 측정 전류에서 계산됨)에서는 전류센서가 후보에 있으면 항상 클램프미터를 요구한다 (H4).**
   - 처음에는 늦게 나타나는 온도 징후로 전류센서를 확정하게 했다. 그랬더니 "부하 증가 + 전류센서 편향"을 전류센서만으로 확정해서 결합 데이터에서 **위험 오분류가 16.7%** 나왔다.
   - 클램프미터 값이 설정값 대비 정상 전류보다 높으면 `load+`(실제 부하 증가) 징후를 붙여 설비 쪽 후보를 남긴다.
6. **E25는 결합이 없을 때만 쓴다.** 결합 모드에서는 토크 상승 자체가 전류센서 탓일 수 있기 때문이다. 클램프미터로 전류센서 이상이 확인됐는데 토크가 3σ 넘게 올라 있으면, 부하 증가도 함께 있다고 본다.
7. **진동 간헐 튐이 징후에 있으면 휴대용 진동계를 60초 대고 최댓값을 기록하게 한다** (E19: 한 순간 측정으로는 못 잡았다).

판정에 쓰는 값은 모두 `config.py`에 있고, 기획서 출처를 옆에 적었다.

## 내부 모의 결과 (개발용, 블라인드 아님)

이 숫자는 **판별기 작성자가 만든 생성기(`sim.py`)로 잰 것**이다. 생성기가 징후표와 같은 가정을 공유하므로 낙관적이다. 성능 주장에 쓰지 않는다.

- 모델은 dev101의 정상 회차 12개로 배웠다.
- dev202와 devc303은 다른 seed로 만든 다른 설비 묶음이다. devc303은 토크 추정값이 100% 측정 전류에서 오고, 결합 스위치를 켜고 쟀다.
- 지표마다 분모가 다르다. 위험 오분류는 설비 이상이 든 회차, 놓침·오분류·보류율은 고장 회차, 정상 오경보는 정상 회차가 분모다. 분모가 0이면 "평가 불가"로 적는다.

| 데이터 (정상/고장/설비 포함) | 단계 | 정답률 | 위험 오분류 | 놓침 | 오분류 | 보류율 | 정상 오경보 | 기대비용 |
|---|---|---|---|---|---|---|---|---|
| dev101 (18/42/24) | 비교 기준 | 40/60 | **4/24** | 2/42 | 13/42 | 0/42 | 1/18 | 4.37 |
| | 도구만 | 35/60 | 0/24 | 2/42 | 0/42 | 22/42 | 1/18 | 0.75 |
| | 현장 확인 1회 후 | 57/60 | 0/24 | 2/42 | 0/42 | 0/42 | 1/18 | 0.75 |
| dev202 (18/62/27) | 비교 기준 | 61/80 | **7/27** | 2/62 | 9/62 | 0/62 | 1/18 | 5.00 |
| | 도구만 | 45/80 | 0/27 | 2/62 | 0/62 | 32/62 | 1/18 | 0.69 |
| | 현장 확인 1회 후 | 75/80 | 0/27 | 2/62 | 2/62 | 0/62 | 1/18 | 0.78 |
| devc303 (12/48/28) | 비교 기준 | 33/60 | **7/28** | 4/48 | 14/48 | 0/48 | 2/12 | 7.30 |
| | 도구만 | 14/60 | 0/28 | 4/48 | 0/48 | 40/48 | 2/12 | 1.43 |
| | 현장 확인 1회 후 | 44/60 | 0/28 | 4/48 | 4/48 | 6/48 | 2/12 | 1.73 |

비교 기준은 보류하지 않아서 처음 정답률은 도구만보다 높다. 대신 진동만 먼저 오르는 베어링 열화, 온도만 오르는 윤활 부족을 센서 탓으로 본다 (위험 오분류).

보류 해소 (처음 보류된 회차만, H2)

| 데이터 | 처음 보류 (그중 정상 회차) | 올바른 해소 | 잘못된 해소 (그중 위험 오분류) | 남은 보류 | 확인 시간 |
|---|---|---|---|---|---|
| dev101 | 22 (0) | 22 | 0 (0) | 0 | 평가 불가 (모의) |
| dev202 | 33 (1) | 30 | 3 (0) | 0 | 평가 불가 (모의) |
| devc303 | 40 (0) | 30 | 4 (0) | 6 | 평가 불가 (모의) |

다시 재는 법:
```bash
python -m engine sim --out /tmp/dev101 --n 60 --seed 101
python -m engine evaluate --data /tmp/dev101 --model engine/models/dev-model.json
python -m engine sim --out /tmp/dev202 --n 80 --seed 202
python -m engine sim --out /tmp/devc303 --n 60 --seed 303 --coupling 1.0
python -m engine evaluate --data /tmp/devc303 --coupled
```

현장 확인 흉내는 정답 폴더(`truth/`)의 실제 물리값에 계측기 잡음을 더한 값이다. 실제 계측기 사양은 아직 모른다.

## 블라인드 평가 (데이터·검증 담당)

판정 엔진 작성자는 블라인드 데이터의 정답(`labels.jsonl`, `truth/`)을 보지 않는다.

1. 데이터·검증 담당이 자기 생성기나 실측 데이터로 `runs/<id>.csv`, `truth/<id>.csv`, `labels.jsonl`을 만든다. 라벨 형식은 `{"run_id", "faults": [코드...], "category": "정상|센서|설비|동시"}`.
2. 정답 없이 판정만 하려면:
   ```bash
   python -m engine batch --runs <폴더>/runs --out preds.jsonl
   python -m engine score --pred preds.jsonl --labels <폴더>/labels.jsonl
   ```
3. 비교 기준도 같은 방식으로: `python -m engine batch --runs <폴더>/runs --out base.jsonl --rule baseline` 뒤 `score --pred base.jsonl`.
4. 실측에서 현장 확인을 실제로 했다면, 확인 결과를 넣어 다시 판정한 카드를 모아 보류 해소를 낸다.
   ```bash
   python -m engine judge --run <폴더>/runs/<id>.csv --check vib=3.1 --jsonl >> after.jsonl   # 확인한 회차마다
   python -m engine score --pred preds.jsonl --pred-after after.jsonl --labels <폴더>/labels.jsonl
   ```
   `after.jsonl`은 확인한 회차의 카드만 한 줄씩 모은 파일이다. 확인하지 않은 회차는 처음 판정이 그대로 남는다.
5. 모의 폴더(`truth/`가 있는 경우)는 한 번에: `python -m engine evaluate --data <폴더>` (비교 기준, 도구만, 현장 확인 1회 후, 보류 해소)
6. 고장 코드: `E_BRG` 베어링 열화, `E_LUB` 윤활 부족, `E_LOAD` 부하 증가, `S_CUR` 전류센서 편향, `S_VIB` 진동센서 편향, `S_VSPK` 진동센서 간헐 튐, `S_TDR` 온도센서 드리프트, `S_TST` 온도센서 고착.

## 알려진 한계

- **모의 데이터만으로 만들었다.** 기대값 모델은 단순 다항식과 두 열 경로다. 실측에서는 맞지 않을 수 있다.
  - `model.py`의 `predict()`만 지키면 학습 모델(예: gradient boosting)로 바꿀 수 있다.
- **아주 작은 드리프트나 윤활 부족은 놓친다** (내부 모의에서 놓침 3~5%).
- **정상 회차에 가짜 온도 징후가 생기면, 현장 확인에서 센서 정상이 나와 설비 후보 "윤활 부족"으로 넘어간다** (E19 ②와 같은 약점). v1.1부터 카드에는 "센서 배제로 남은 후보, 원인 미확정"으로 적지만, 채점에서는 여전히 정상 오경보다.
- **간헐 튐이 확인하는 60초 안에 나타나지 않으면 센서 정상으로 본다.**
- **온도 고착 찾기는 흔들림이 거의 없는 것을 본다.** 실제 센서가 0.1 °C 단위로 끊겨 나오면 오경보가 날 수 있다.
- **결합 데이터에서 정상 오경보가 16.7%로 높다.** 원인은 아직 못 찾았다.
- **현장 확인 시간·기록 방식·허용오차(`config.py`의 `TOLERANCE`, `CHECK_TOOLS`)는 예시값이다.** 현업 절차와 실제 계측기 사양으로 바꿔야 한다. 카드에도 예시값이라고 표시한다.
- **비교 기준(현장 첫 판단 규칙)은 우리가 만든 단순 규칙이다.** 실제 현장 판단을 대표한다고 말하지 않는다. "단순 규칙보다 낫다"까지만 말한다.
