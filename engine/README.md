# 판정 엔진 (재작성 v1)

설비 알람의 측정값을 보고 센서 문제인지 설비 문제인지 가린다. 못 가리면 확정하지 않고, 무엇을 한 번 재면 갈리는지 알려 준다. 결과는 판정 카드(JSON)로 낸다.

기획서 v0.4~v0.7, results.html, SCQA 기획안에 적힌 판정 논리를 새로 구현했다. **이전 v0.7 코드는 남아 있지 않아서, 기획서의 숫자(블라인드 1~8, 위험 오분류 1.8% 등)는 이 코드로 재현되지 않는다.** 숫자는 새 블라인드 데이터로 다시 잰다.

## 빠른 시작

Python 3.10 이상, numpy만 있으면 된다. 명령은 레포 루트에서 실행한다.

```bash
pip install -r engine/requirements.txt

# 판정 한 번 (기획서 6번 사례: 베어링 열화 + 온도센서 고착)
python -m engine judge --run engine/tests/example-06.csv

# 현장 확인 결과를 넣어 다시 판정 (휴대용 진동계 3.95 mm/s)
python -m engine judge --run engine/tests/example-06.csv --check vib=3.95

# 판정 카드 API (화면·LLM 연동용)
python -m engine serve --port 8000

# 테스트
python -m pytest engine/tests -q
```

기본 모델 `engine/models/dev-model.json`은 내부 모의 정상 회차 12개로 배운 개발용이다. 실측 데이터를 쓰면 그 정상 구간으로 다시 배운다.

```bash
python -m engine train --normal <정상 운전 CSV 폴더> --out engine/models/<이름>.json
```

## 입력 형식

1초 간격 CSV. 열 이름은 아래와 같아야 한다.

| 열 | 뜻 | 단위 |
|---|---|---|
| `t` | 운전 시작부터 지난 시간 | 초 |
| `setpoint` | 속도 설정값 | % |
| `torque` | 인버터 토크 추정값 | % 정격 |
| `current` | 모터 전류 | A |
| `vib` | 진동 (RMS) | mm/s |
| `temp` | 모터 온도 | °C |

- 처음 30~150초는 설비별 재보정 구간이다. 고장이 이 구간 안에 있으면 재보정이 고장을 흡수한다.
- 징후는 150초 이후부터 찾는다.

## 판정 흐름 (기획서 대응)

| 단계 | 하는 일 | 코드 |
|---|---|---|
| ① 가상센서 | 정상 운전에서 설정값→토크, 토크→전류, 설정값→진동, 토크 이력→온도(빠른·느린 두 열 경로)를 배운다 | `model.py` |
| 재보정 | 30~150초 잔차 중앙값을 0으로 맞춘다 | `detect.py` |
| 징후 | 잔차가 4σ를 넘어 이어지면 징후로 본다. 설정값 변경 직후 40초는 문턱 1.75배. 진동 간헐 튐과 온도 고착은 따로 찾는다 | `detect.py` |
| ② 후보 | 고장 징후표(설비 3, 센서 5)로 징후를 설명하는 후보를 남긴다 | `signatures.py`, `judge.py` |
| 판정 | 후보가 모두 설비 쪽이면 확정(설비), 모두 센서 쪽이면 확정(센서), 모두 설비+센서면 확정(동시 이상). 섞이면 늦은 징후로 가를 수 있을 때 확인 대기(온도 지연의 2배까지), 아니면 정보 부족 + 현장 확인 항목 | `judge.py` |
| ④ 갱신 | 휴대용 계측 결과를 넣으면 후보를 줄여 다시 판정한다 | `judge.py` |

## 판정 카드

예시: `schemas/verdict-card.example.json`(현장 확인 전), `schemas/verdict-card.after-check.example.json`(진동계 확인 후).

| 필드 | 뜻 |
|---|---|
| `verdict` | `정상` / `확정` / `확인 대기` / `정보 부족` |
| `verdict_detail` | 확정일 때 `센서` / `설비` / `동시` |
| `evidence_status` | `측정 확인됨` / `측정 의심` / `확인 대기` / `정보 부족` |
| `handoff_to_guide` | 정비 가이드(LLM)로 넘겨도 되는가. 측정 확인됨일 때만 `true` |
| `suspect_sensors` | 믿으면 안 되는 센서. 동시 이상일 때 정비 가이드에 이 값은 빼고 넘긴다 |
| `findings` | 고장마다 `확정` 또는 `후보` |
| `candidates` | 징후를 설명하는 고장 조합 목록 |
| `check` | 다음 현장 확인: 계측기, 위치, 시간, 기록 방식, 결과별로 남는 후보 |
| `wait_until_s` | 확인 대기일 때 다시 볼 시각 |
| `checks_applied` | 넣은 현장 확인 결과와 판단 (휴대용 값, 설치 값, 가상센서 값, 허용오차) |
| `values` | 관련 채널의 설치 센서 값과 가상센서 값 |
| `symptoms`, `reasons` | 보인 징후와 판단 이유 (화면에 그대로 쓸 수 있는 문장) |

API는 `POST /judge`에 `{"run": {열: [값...]}, "coupled": false, "checks": [...]}`를 보내면 판정 카드를 돌려준다.

## 재작성하면서 정한 것 (기획서에 없던 것)

1. **단일 고장 우선.** 단일 고장으로 설명되면 단일 후보만 남기고, 아니면 이중 후보를 남긴다.
   - 기획서는 "단일·이중 후보를 모두 남김"이었지만, 그러면 늦은 징후가 나타나도 후보가 갈리지 않았다.
2. **진동 기대값은 설정값만으로 계산한다.** 정상 데이터에서는 토크가 설정값에 묶여 있어 둘의 효과를 가를 수 없다. 토크를 넣었더니 부하가 바뀔 때 가짜 "진동 낮음" 징후가 나왔다.
3. **설비별 이득 차이만큼 문턱을 넓힌다.** 재보정은 오프셋만 맞춘다. 운전점이 재보정 구간에서 멀어지면 설비마다 다른 이득이 가짜 징후를 만든다. 정상 회차에서 잔차 기울기를 재서, 그 RMS의 `alpha_k`배만큼 문턱을 넓힌다.

   | 여유 배수 | dev101 기대비용 | dev202 기대비용 | 위험 오분류 |
   |---|---|---|---|
   | 1배 | 0.77 | 1.24 | dev202 1.6% |
   | **2배 (채택)** | **0.75** | **0.78** | **0%** |
   | 3배 | 1.90 | 1.98 | 2.4%, 3.2% (둔해져서 설비 징후를 놓침) |

4. **현장 확인 판단 방식.**
   - 휴대용 값과 설치 값의 차이가 계측기 허용오차 안이면 센서 정상으로 본다.
   - 허용오차를 넘으면 설치 값과 가상센서 값 중 휴대용 값에 가까운 쪽으로 판단한다 (E30).
   - 고정 허용오차(1 °C)만 썼을 때는 작은 온도 드리프트를 "센서 정상"으로 잘못 봤다.
5. **결합 모드(토크 추정값이 측정 전류에서 계산됨)에서는 전류센서가 후보에 있으면 항상 클램프미터를 요구한다 (H4).**
   - 처음에는 늦게 나타나는 온도 징후로 전류센서를 확정하게 했다. 그랬더니 "부하 증가 + 전류센서 편향"을 전류센서만으로 확정해서 결합 데이터에서 **위험 오분류가 16.7%** 나왔다.
   - 클램프미터 값이 설정값 대비 정상 전류보다 높으면 `load+`(실제 부하 증가) 징후를 붙여 설비 쪽 후보를 남긴다.
6. **E25는 결합이 없을 때만 쓴다.** 결합 모드에서는 토크 상승 자체가 전류센서 탓일 수 있기 때문이다. 클램프미터로 전류센서 이상이 확인됐는데 토크가 3σ 넘게 올라 있으면, 부하 증가도 함께 있다고 본다.
7. **진동 간헐 튐이 징후에 있으면 휴대용 진동계를 60초 대고 최댓값을 기록하게 한다** (E19: 한 순간 측정으로는 못 잡았다).

판정에 쓰는 값은 모두 `config.py`에 있고, 기획서 출처를 옆에 적었다.

## 내부 모의 결과 (개발용, 블라인드 아님)

이 숫자는 **판별기 작성자가 만든 생성기(`sim.py`)로 잰 것**이다. 생성기가 징후표와 같은 가정을 공유하므로 낙관적이다. 성능 주장에 쓰지 않는다.

- 모델은 dev101의 정상 회차 12개로 배웠다.
- dev202와 devc303은 다른 seed로 만든 다른 설비 묶음이다.

| 데이터 | 단계 | 정답률 | 위험 오분류 | 놓침 | 오분류 | 보류율 | 확정 정확도 | 정상 오경보 | 기대비용 |
|---|---|---|---|---|---|---|---|---|---|
| dev101 (60회) | 도구만 | 58.3% | 0% | 4.8% | 0% | 52.4% | 100% | 5.6% | 0.75 |
| | 현장 확인 1회 후 | 95.0% | 0% | 4.8% | 0% | 0% | 100% | 5.6% | 0.75 |
| dev202 (80회) | 도구만 | 56.2% | 0% | 3.2% | 0% | 51.6% | 100% | 5.6% | 0.69 |
| | 현장 확인 1회 후 | 93.8% | 0% | 3.2% | 3.2% | 0% | 96.7% | 5.6% | 0.78 |
| devc303 결합 100% (60회), 스위치 끔 | 도구만 | 36.7% | 0% | 8.3% | 8.3% | 58.3% | 75.0% | 16.7% | 1.43 |
| | 현장 확인 1회 후 | 70.0% | 0% | 8.3% | 10.4% | 14.6% | 86.5% | 16.7% | 1.48 |
| devc303, 스위치 켬 | 도구만 | 23.3% | 0% | 8.3% | 0% | 83.3% | 100% | 16.7% | 1.43 |

다시 재는 법:
```bash
python -m engine sim --out /tmp/dev101 --n 60 --seed 101
python -m engine evaluate --data /tmp/dev101 --model engine/models/dev-model.json
```

현장 확인 흉내는 정답 폴더(`truth/`)의 실제 물리값에 계측기 잡음을 더한 값이다. 실제 계측기 사양은 아직 모른다.

## 블라인드 평가 (데이터·검증 담당)

판정 엔진 작성자는 블라인드 데이터의 정답(`labels.jsonl`, `truth/`)을 보지 않는다.

1. 데이터·검증 담당이 자기 생성기나 실측 데이터로 `runs/<id>.csv`, `truth/<id>.csv`, `labels.jsonl`을 만든다. 라벨 형식은 `{"run_id", "faults": [코드...], "category": "정상|센서|설비|동시"}`.
2. 정답 없이 판정만 하려면:
   ```bash
   python -m engine batch --runs <폴더>/runs --out preds.jsonl
   python -m engine score --pred preds.jsonl --labels <폴더>/labels.jsonl
   ```
3. 현장 확인 1회까지 보려면: `python -m engine evaluate --data <폴더>`
4. 고장 코드: `E_BRG` 베어링 열화, `E_LUB` 윤활 부족, `E_LOAD` 부하 증가, `S_CUR` 전류센서 편향, `S_VIB` 진동센서 편향, `S_VSPK` 진동센서 간헐 튐, `S_TDR` 온도센서 드리프트, `S_TST` 온도센서 고착.

## 알려진 한계

- **모의 데이터만으로 만들었다.** 기대값 모델은 단순 다항식과 두 열 경로다. 실측에서는 맞지 않을 수 있다.
  - `model.py`의 `predict()`만 지키면 학습 모델(예: gradient boosting)로 바꿀 수 있다.
- **아주 작은 드리프트나 윤활 부족은 놓친다** (내부 모의에서 놓침 3~5%).
- **정상 회차에 가짜 온도 징후가 생기면, 현장 확인에서 센서 정상이 나와 "윤활 부족"으로 판정된다** (E19 ②와 같은 약점).
- **간헐 튐이 확인하는 60초 안에 나타나지 않으면 센서 정상으로 본다.**
- **온도 고착 찾기는 흔들림이 거의 없는 것을 본다.** 실제 센서가 0.1 °C 단위로 끊겨 나오면 오경보가 날 수 있다.
- **결합 데이터에서 정상 오경보가 16.7%로 높다.** 원인은 아직 못 찾았다.
- **현장 확인 허용오차(`config.py`의 `TOLERANCE`)는 자리표시 값이다.** 실제 계측기 사양으로 바꿔야 한다.
