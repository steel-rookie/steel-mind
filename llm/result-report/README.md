# 결과 보고서 프로토타입

한 판이 끝난 뒤 보여 줄 운영 결과 보고서입니다. 틀과 숫자는 규칙으로 바로 그리고, 문장 칸만 LLM(Gemini)에게 백그라운드 작업으로 맡깁니다.

## 실행

1. 루트 `.env`에 `GEMINI_API_KEY`를 넣습니다(`GEMINI_MODEL`은 비우면 `gemini-2.5-flash`).
2. `python llm/result-report/server.py`
3. 브라우저에서 http://localhost:8791 을 엽니다. 포트는 `REPORT_PORT`로 바꿀 수 있습니다.

키가 없거나 서버 없이 `index.html`을 파일로 열어도 화면은 기본 문장으로 끝까지 동작합니다.

## 무엇을 누가 만드나

| 칸 | 만드는 쪽 |
|---|---|
| 결과 ID, 운영 성향 유형, 레이더, 효율·순위, 사건별 기록, 회차별 성향 분포 | 규칙(`index.html`) |
| 사건별 공장장 회의(선택 직후) | 규칙. 내 추천을 골랐으면 그 공장장의 `why`로 찬성, 아니면 공장장별 불만 틀(4줄) 하나에 고른 선택과 내 추천을 넣음. 선택지에 `reactions`(agent·stance·line)가 있으면 그 대사를 먼저 씀 |
| 선택 DB 탭 | 규칙. 사건 × 선택지 18개 기록(추천, 일어난 일, 지표별 손실, 회의 대사)을 한 표로. 지금 고른 선택은 강조 |
| 한 줄 총평, 결정적 순간, Agent 한마디, 다음 판 제안 | LLM. 먼저 기본 문장을 보여 주고, AI 문장이 오면 칸마다 바꿔 끼움 |

## 사건은 서로 독립

사건 6개를 독립 변수로 봅니다. 앞 사건의 선택이 뒤 사건에 손실을 더하지 않으므로(시나리오의 `carry`는 쓰지 않음) 한 판의 결과는 선택 DB에서 고른 기록 6개의 합입니다. 판과 판 사이에는 회차 번호(와 성과 탭 누적 기록)만 이어집니다. 그래서 회의 대사는 경로 729가지가 아니라 사건 × 선택지 18장면(69줄)만 있으면 됩니다.

## 백그라운드 작업 흐름

1. 화면이 판 기록을 `POST /api/report/jobs`로 보내면 서버는 바로 `job_id`를 돌려주고, 스레드에서 Gemini를 부릅니다.
2. 화면은 `GET /api/report/jobs/<id>`로 0.8초마다 상태를 묻습니다(최대 90초).
3. 끝나면 칸마다 검사합니다. 비었거나, 글자 수를 넘었거나, 숫자가 들어 있으면 그 칸은 기본 문장을 남깁니다.
4. 같은 경로(시나리오 ID + 결과 ID)의 결과는 `.cache/`에 저장해 다시 부르지 않습니다.

LLM에는 손실을 숫자 대신 말(작은 손실, 큰 손실 등)로 보내고, 숫자를 쓰지 말라고 지시합니다. 숫자는 규칙 칸에만 나옵니다.
API 키는 서버에만 있고, 요청 헤더(`x-goog-api-key`)로 보내 URL에 남지 않습니다.

## 파일

- `index.html`: 보고서 화면과 규칙 계산, 기본 문장, 칸별 검사
- `scenario.js`: 열간압연 시나리오(사건 6개 × 선택지 3개 = 729가지 경로). 결말 로드맵(729.html)의 데이터와 같음
- `server.py`: 화면 파일 제공과 백그라운드 작업(표준 라이브러리만 사용)
